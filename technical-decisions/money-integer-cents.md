# 金额整数分与零误差转换

- 决策日期：2026-08-03
- 类型：技术决策
- 状态：已实施（v0.1.0 已落地，`pkg/money.Cents` 已实现并有测试覆盖；2026-08-03 修订 `UnmarshalJSON` 为纯整数解析，彻底去除浮点）
- 来源：[conventions.md 关键设计约束 #3 与「金额与折扣计算」](https://github.com/quanttide/qtcloud-pay/blob/main/src/provider/docs/conventions.md)

## 背景

支付/账本系统中金额是最敏感的数据，浮点表示会引入舍入误差，可能导致余额、对账、结算出现分毫级偏差。需要统一金额的存储表示与 API 传输格式，保证全链路零误差。

## 决策

**内部全链路金额用 int64（分）存储与计算，禁止浮点金额**；API 边界经 `pkg/money.Cents` 转换：

- **内部**：账本、余额、交易、券、订单全部以分（int64）参与计算，不经过浮点舍入
- **传输**：API 边界以元（两位小数数字，如 `99.99`）传输，符合人的直觉；严格校验最多两位小数，拒绝三位及以上小数（拒绝 `99.999`），避免静默舍入入账
- **转换**：分 ↔ 元 转换零误差

## 实现约定

`pkg/money.Cents`（`int64` 别名）承担边界转换：

- `MarshalJSON` 分 → 元：纯整数运算（`v/100` 与 `v%100`，`%02d` 补零），如 `9999 → "99.99"`，负数正确带符号
- `UnmarshalJSON` 元 → 分：纯整数字符串解析（`ParseInt`，不经浮点）——按 `.` 切分整数部分与小数部分，小数补零到两位后拼入分；严格校验最多两位小数（拒绝 `99.999`），拒绝字符串形式与指数记法（如 `"99.99"`、`1e3`）
- 测试覆盖：正负值、两位小数、三位小数拒绝、字符串/指数记法拒绝、往返一致性（`9999 → 99.99 → 9999`，含负数）

折扣计算同为整数运算，与金额表示一致：

- 折扣券：整数百分比，9 折 = rate 90 = 省 10%，`折扣 = 应付 × (100 − rate) / 100`（向下取整）
- 满减券：应付 ≥ threshold 时减 amount
- 代金券：抵扣 `min(面值, 剩余应付)`

## 例外与遗留

1. **`POST /reconcile/bank` 银行流水 CSV**：金额为分（`amount_cents`，财务工具格式），不经过 `Cents` 元传输
2. **v0.1.0 已知遗留（见 ROADMAP F2）**：`internal/channel` 渠道层仍用 float64 元（如 `PayRequest.Amount`），且存在 `int(x*100)` 截断精度缺陷——渠道层与账本层金额表示不一致。**新代码一律以分传输，勿照抄渠道层写法**

## 结果

- 账本核心链路（充值/发券/消费/核销/结算）金额计算全部为整数运算，无浮点误差，对账与结算可信
- API 对超精度金额（≥3 位小数）显式报错而非静默舍入，入账金额与用户所见一致
- 遗留的渠道层 float64 表示是 v0.1.0 刻意保留的边界（渠道尚未入账），需在 v0.2.0 支付闭环（ROADMAP T5/F3）前按本决策收敛
