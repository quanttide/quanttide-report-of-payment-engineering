# 金额整数分与零误差转换

- 决策日期：2026-08-03（首次决策）
- 修订日期：2026-08-03（传输层由元改为整数分；金额值对象采用 go-money）
- 类型：技术决策
- 状态：已决策，实施中（v0.1.0 已落地内部整数分；传输层契约与工具库对齐中）
- 来源：[conventions.md 关键设计约束 #3](https://github.com/quanttide/qtcloud-pay/blob/main/src/provider/docs/conventions.md)；工具库 `quanttide-pay-toolkit/packages/go/pkg/money`

## 背景

支付/账本系统中金额最敏感：二进制浮点（IEEE 754）会引入舍入误差，可能导致余额、对账、结算出现分毫级偏差。需要统一金额的存储、计算与传输表示，保证全链路零误差，并避免各应用重复实现。

## 决策

1. **全链路整数分**：金额一律以货币最小单位（分）的 int64 存储、计算与**传输**，禁止浮点金额——内部（账本、余额、交易、券、订单）与 API 边界单位一致，不存在元↔分换算，因此"三位小数静默舍入"这类问题没有存在空间
2. **以 go-money 为事实标准**：金额值对象采用 Go 社区标准库 `github.com/Rhymond/go-money`（v1.0.15，int64 最小单位 + ISO 4217 币种），工具库 `pkg/money` 以类型别名直接复用其完整 API（构造、加减、比较、Split/Allocate 分账、Display 格式化），不重复实现
3. **JSON 契约**：`{"amount": <整数分>, "currency": "<ISO 4217 币种>"}`——与 go-money 默认格式一致；amount 必须为整数（拒绝小数、字符串、指数记法），币种必须有效，非零金额必须携带币种
4. **元仅存在于展示层**：`Display()`/前端负责将分格式化为元（如 ¥99.99），存储与传输均不出现元

## 修订说明（2026-08-03）

- 原 v0.1.0 约定为"传输元、内部分"（`Cents` 边界转换，严格校验两位小数）。引入完整 Money 值对象后重新审视：传输层与内部同用分，与库默认、行业惯例（Stripe、微信支付 `total_fee`）一致，且对账 CSV（`amount_cents`）天然同单位；"元"退居展示层
- 原 `pkg/money.Cents` 类型随提炼移除；其纯整数解析经验（拒绝超精度输入、不经浮点）保留为反序列化校验的基础

## 实现约定

工具库 `pkg/money`（go-money 类型别名 + 注入点覆盖）：

- `MarshalJSON`：整数分输出，与 go-money 默认一致
- `UnmarshalJSON`：覆盖 go-money 默认实现（其经 float64 解析并 `int64()` 截断，非整数会静默舍入，与本决策冲突）——纯整数 `ParseInt` 校验：仅接受 JSON 整数；未知币种拒绝；非零金额缺币种拒绝；零金额可空币种
- provider（qtcloud-pay）transport：DTO 金额字段使用 `*money.Money`，请求/响应金额为整数分 JSON

测试覆盖：整数往返、非整数拒绝（小数/字符串/指数）、未知币种拒绝、跨币种运算报错、Split 分账余数分配、Display 格式化。

## 例外与遗留

1. 银行流水 CSV `amount_cents`：本就是分，与 API 同单位，无需换算
2. **v0.1.0 已知遗留（见 ROADMAP F2）**：`internal/channel` 渠道层仍用 float64 元（如 `PayRequest.Amount`）且存在 `int(x*100)` 截断精度缺陷——渠道层与账本层金额表示不一致。**新代码一律以分传输，勿照抄渠道层写法**；v0.2.0 支付闭环（ROADMAP T5/F3）前收敛

## 结果

- 内部、传输、对账单位统一为分，消除单位换算与超精度静默舍入整类缺陷
- 金额能力（运算、分账、格式化、币种校验）直接来自成熟库，跨应用复用（工具库）
- 渠道层 float64 遗留是 v0.2.0 前唯一金额精度风险点
