# order 订单与结算

- 决策日期：2026-08-03
- 类型：技术决策
- 状态：已决策，已实施
- 来源：qtcloud-pay `docs/order.md`；`src/provider/internal/order/`

## 背景

M3 需要把券、余额、账本串成一个完整下单流程：应用计费规则 → 核销券/扣余额 → 写消费与核销交易。涉及五个模块的状态变更，若不做统一编排，会出现"券核销了但余额没扣""交易缺条"等部分成功。

## 决策

1. **order 是结算编排者，单事务协调**：`Settle` 在一个数据库事务内完成——查订单（幂等）→ 锁账户 → 取可用券 → `billing.Calculate` → 执行计划（核销券/扣余额）→ 写消费/核销交易 → 落订单——余额、券状态、交易、订单四者要么全部提交要么全部回滚（不错）
2. **幂等 = `order.id`（商户订单号）唯一**：重复 `POST /orders` 返回已有订单，不重复结算；账本侧消费/核销交易用 `settle:{order_id}[:redeem:{kind}:{ref}]` 幂等键兜底
3. **账户行锁 = 同账户全部结算的串行化点**：`Settle` 先 `GetForUpdate` 锁账户行，同账户的结算、充值、退款全部串行；券核销因此无需依赖券锁（`coupon/voucher.Use` 的 `GetForUpdate` 是双保险而非主依赖）——并发正确性依赖 READ COMMITTED 下的"锁后重读"（锁前读到的只作存在性判断）
4. **余额不足不落库**：返回业务错误（HTTP 422），订单不落库——v0.1.0 刻意不引入 failed 订单状态
5. **结算计划快照**：`SettleDetail`（JSON）记录逐项抵扣明细，订单可查历史结算结果，不受规则变更影响
6. **依赖注入**：对 billing/coupon/voucher/account/transaction 声明最小接口（`accountSvc`/`couponSvc`/…），单测 mock 验证编排顺序

## 理由

- 单事务是"不错"的最简实现：跨模块写不需要分布式事务或补偿，所有状态在一条数据库事务内原子提交
- 账户行锁而非券锁：同账户资金操作天然串行，一把锁覆盖全部路径，并发模型简单可推理
- 快照防"历史订单被新规则改写"：结算结果以快照为准，规则演进不影响已结算订单

## 结果

- 结算正确性由单事务 + 行锁保证，三层测试覆盖完整链路（充值 → 发券 → 消费 → 余额与账本一致）
- 已知遗留：无 failed 订单状态（下单失败即不落库，客诉场景无法区分"从未下单"与"失败"）；规则顺序改代码固定（见 billing 决策）
