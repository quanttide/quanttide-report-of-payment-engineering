# account 账户与余额

- 决策日期：2026-08-03
- 类型：技术决策
- 状态：已决策，已实施
- 来源：qtcloud-pay `docs/account.md`；`src/provider/internal/account/`

## 背景

M1 需要客户的资金入口：对公打款入账（充值登记）与多退登记（退款出账），以及余额查询。账本模块体系里，账户是"余额"这一事实的持有者，但余额不能与交易记录脱节——否则无法审计、无法对账。

## 决策

1. **账户 = 客户虚拟钱包**：`Account{ID, CustomerID, Balance}`，ID 为业务号（`acc_` 前缀 + 密码学安全随机）；余额单位为分
2. **余额是交易的投影，不单独记账**：余额的单一事实来源是交易账本（`transaction`）；余额与交易**同事务**更新（锁账户行 → 改余额 → `transaction.Append` 写充值/退款交易），提交后两者必然一致
3. **充值/退款对称登记**：幂等键 = 打款/退款凭证号（`recharge:{voucher_no}` / `refund:{voucher_no}`），先查后插，唯一约束冲突时整体回滚并视为成功（不重）
4. **账户行锁（`GetForUpdate`）**：同账户的并发充值/退款/结算以账户行锁串行化，防并发重复入账；`BalanceAfter` 快照在锁内计算
5. **边界校验**：金额必须为正整数（分）；退款余额不足整体回滚（HTTP 422）；凭证号必填（防键空间污染由 `pkg/idempotency` 兜底，见幂等键契约）

## 理由

- 余额投影而非独立账本：避免"余额表与交易表双写不一致"这一类账务系统最隐蔽的错误；对账（reconciliation）正是靠"余额 = Σ 交易"验证正确性
- 凭证号幂等 + 冲突回滚视为成功：人工登记场景下重复提交（或并发）不会造成重复入账，且调用方无需感知重试语义

## 结果

- 不丢、不重、可查：充值/退款可追溯至凭证号与交易记录
- 已知遗留（v0.2.0）：人工登记模式将被渠道回调自动入账替代（幂等键 = 渠道交易号），模型不变，变的只是交易来源
