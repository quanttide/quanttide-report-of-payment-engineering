## 复盘范围与结论

本次复盘覆盖服务端 v0.1.0 账本核心从立项到 `provider/v0.1.0-alpha.4` 部署的全过程：领域如何定位、账本交付了什么、产品缺口为何存在、生产链路卡在哪里。

结论有三条。账本骨架已经成立，客户交易事实有了可靠载体；产品价值尚未兑现，因为还没有真实业务跑在上面；部署链路已推进到镜像构建之前，阿里云 ACR 是当前唯一硬阻塞，根因已定位且修复已进入 workflow，剩余一项人工前置。

## 领域定位

支付工程不处理财务问题，只确保公司与客户之间交易的可靠性，并让交易处理从手动演化到自动。它与财务管理是正交的两个领域：财务回答「这笔钱对公司意味着什么」，支付工程回答「这笔交易对客户是否可靠」。

从客户视角，可靠性由四层保证构成。不丢，每一笔打款、发券、核销都有记录，迁移过程不丢单；不重，重复操作不会让发券、充值、扣款生效两次；不错，客户看到的余额、优惠与订单状态和系统内部一致；可查，任何一笔交易都能追溯，客诉时可以查证。计费规则也属于可靠性的一部分，规则不清楚，客户就会认为系统算错了。

可靠性的执行方式分三个阶段演进：手动登记时表格就是账本；系统化之后登记动作数字化、规则固化；自动化阶段接入真实支付，由系统完成入账与核销。三个阶段的可靠性要求一致，变化的是由谁保证。

建模的核心对象不是钱，而是客户交易的记录与状态，以及保证这些事实一致性的机制。这决定了账本必须 append-only、写入有唯一入口、状态可回放。

「支付工程」这一命名是权衡后的结果。它不是支付通道，微信与支付宝的通道能力完善且可替换；不是财务账务，那属于财务管理；也不是范围过宽的交易工程；而是客户交易可靠性的工程化。命名从早期的支付接口统一，经过交易工程的尝试，最终落在支付工程。

## 账本核心交付

v0.1.0 把「客户欠我们多少、我们欠客户什么」从人脑和表格搬进了系统账本，并刻意绕开支付接口，先用模拟账户让业务跑起来。

对客户而言，交付了一个明确的钱包，充值、消费与余额清晰；券成为看得见的权益，发放时间、有效期与使用状态可查；每一笔交易都能追溯，对应领域边界中的不丢、不重、不错、可查。

对业务运营而言，批量发券一次一批且重复操作不会重复发放；对公打款落地成充值登记，凭证号幂等；余额与账本可以互相校验，银行流水可以核对。

对未来的支付自动化而言，最关键的一点是账本不变，变的只是钱的来源。今天手工登记的充值，明天就是支付回调写入的同一笔，免费期到付费期不需要推倒重来。

## 产品缺口

### 计费规则仍是代码默认值

优惠券何时使用、代金券是否优先于余额、优惠力度如何，都属于业务决策。当前实现采用满减、折扣、代金券、余额的固定顺序，相当于技术替业务拍板，但从未与业务确认。规则一旦错误，客户就会认为系统算错了。

### 按量计费尚未支持

课程与数据服务按一口价结算，现有模型足够；云服务是 PaaS 按量计费，统一按订单金额结算的简化在按量场景会失效。云服务业务若先跑起来，这里会暴露问题。

### 交付的是服务端而非产品

当前能力全部是 API：没有运营后台，发券与登记打款依赖调接口；没有客户自助界面，客户看不到自己的余额与券；没有权限与操作审计，无法回答谁能发券、谁登记了打款。真实业务中，运营与财务不可能每天敲 API。

### 缺口成因

三个缺口对应三种不同性质，不能混为一谈。计费规则属于决策未完成，文档只能记录当前默认值，答案必须由业务给出；按量计费与支付渠道属于有意后置，路线图写明了不做以及为什么不做；运营后台、客户自助与权限审计属于范围之外，v0.1.0 的范围是账本核心 API 层，在业务未验证前设计运营后台等于想象需求。

产品回顾的意义，是把这些「范围之外、决策未定」的事情从隐性变成显性，让它们成为明确记录、等待决策的事项。

## 部署与 CI

生产部署在阿里云。计算使用函数计算 FC 3.0，以 custom-container 运行容器镜像，VPC 内网访问 RDS；数据库使用 RDS PostgreSQL Serverless，PG 18，可用区 cn-hangzhou-k；镜像存放在阿里云 ACR 个人版公开仓库，由 FC 同地域直拉。

基础设施分两层。系统级资源包括 VPC、交换机、安全组与 RDS 实例，由 quanttide-platform 仓库的 terraform 管理，qtcloud-pay 通过 `terraform_remote_state` 引用；应用级资源包括数据库与账号、FC 函数与默认角色，由 qtcloud-pay 仓库管理。命名遵循归属、应用、组件三段式，环境后缀显式化。

发布由 `provider/*` tag 触发 CI：多阶段构建镜像，同一镜像双通道推送 Docker Hub 与 ACR，随后执行 terraform apply 创建数据库、账号与 FC 函数。发布入口是 `qtcloud-devops release publish`，负责校验 CHANGELOG、打 tag 与创建 GitHub Release。

凭证体系覆盖本地、CI 与运行时三类：本地使用 aliyun 配置 profile，CI 使用组织级 AccessKey、ACR 登录凭证、数据库密码与 Docker Hub 凭证。生产保护包括 RDS 与 VPC 的 `prevent_destroy`、删除保护、OSS 状态桶版本控制，以及部署所挂的 GitHub production 环境。

## 故障复盘

### alpha.4 的 ACR 阻塞

`provider/v0.1.0-alpha.4` 已发布，CI 阻塞在 Build and Push，Docker Hub 通道正常，ACR 报 `insufficient_scope: authorization failed`。根因是 ACR 仓库从未创建成功。

幂等创建步骤存在三重失效。凭证未注入，`aliyun/aliyun-cli-action@v1` 实际只接受 `version` 输入，传入的 access key 与 region 参数全部无效；API 参数是旧格式，当前 aliyun CLI 的 `cr` 产品为实例版 API，`CreateNamespace` 与 `CreateRepository` 必填 `--InstanceId`，workflow 使用的老版参数必然报缺参；错误被吞，创建步骤用重定向加 `|| echo "already exists"` 静默处理，CI 误以为命名空间与仓库已存在。

修复已进入 workflow：改用 `aliyun/setup-aliyun-cli-action@v1` 只安装 CLI，凭证改为 job 环境变量；先查询个人版实例 ID，为空即报错提示控制台开通，再按实例版参数创建资源；去掉吞错逻辑，查询存在、不存在再创建、创建失败即失败。

剩余一项人工前置：ACR 个人版实例需要在控制台开通；如果 CI 的 AccessKey 与 ACR 登录凭证不属于同一主账号，Ensure 步骤仍会失败，需要统一账号或手动创建命名空间与仓库。

### 历史失败对照

| 版本 | Build and Push | Terraform 阶段失败点 |
|:--|:--|:--|
| alpha.1 | 通过 | Init，OSS 远程状态 |
| alpha.2 | 通过 | Validate |
| alpha.3 | 通过 | Apply |
| alpha.4 | 失败，ACR insufficient_scope | 未执行，前置失败 |

### 部署层面的已知风险

FC 中国区无法拉取 Docker Hub，部署镜像必须走同地域 ACR；ACR 个人版的 terraform 资源已弃用，只能由 CI 幂等创建；PG 18 Serverless 的官方文档说法过时，应以升级预检查 API 为准，b 区无库存，必须使用 k 区；RDS Serverless 的计费方式必须是 Serverless，授权类型是 DBOwner；服务关联角色需要账号级一次性创建；terraform apply 可中断，中断后需要 import 未入 state 的资源；数据库密码目前明文落在 tfstate，属于待改的最小化实现。

## 经验

- 边界先定，交付才有尺度。领域边界明确了不做什么，产品范围才能稳定，缺口也才能被准确归类。
- 决定不做的要写明为什么。有意后置与决策未完成是两种状态，前者可以按路线图推进，后者必须回到业务。
- 产品价值由真实业务兑现。账本骨架再完整，没有第一笔充值、第一批发券、第一位查账的客户，价值仍是空白支票。
- 失败必须暴露。静默处理错误会把「资源不存在」伪装成「已存在」，让故障延后到更难定位的位置。
- 基础设施文档不能替代 API 验证。区域库存、资源弃用、参数版本都以实际接口返回为准。
- 凭证与账号的一致性要前置确认。CI 的隐性前提是同一主账号、同一地域、同一实例，缺一项都会在最后一步失败。

## 下一步

| 优先级 | 事项 | 理由 |
|:--|:--|:--|
| P0 | 与业务确认计费规则，明确时机、优先级与力度 | 规则错误会直接表现为客户认为系统算错 |
| P0 | 选一块业务，建议课堂，端到端跑通 | 所有设计尚未经过真实业务验证，这是最大的产品风险 |
| P0 | 开通 ACR 个人版实例并统一主账号 | 解除 alpha.4 之后的部署阻塞 |
| P1 | 运营后台：发券、登记打款、查询流水 | 日常高频操作不能依赖 API |
| P1 | 客户自助查询：余额、流水、我的券 | 可靠性要客户看得见才算数 |
| P2 | 支付渠道接入 | 计划内后置，自动付费需求尚不强烈 |
| P2 | 按量计费支持 | 等云服务业务出现真实需求再做 |

## 结语

技术上，账本骨架已经合格，领域边界、可靠性定义与部署路径都已清晰。产品上，它仍是一张等待兑现的支票，价值取决于业务何时真正用起来。部署上，剩余问题已收敛为一项人工前置，不再是不可定位的故障。下一阶段的关键动作不是继续加代码，而是把计费规则谈清楚，并让第一块业务跑通。
